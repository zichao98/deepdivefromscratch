Git & GitHub from zero to hero

Every software team on earth uses Git. It's an undo button for your whole project, a way to try ideas without breaking anything, and the way people work on the same code without overwriting each other. Learn it here in a safe sandbox: a real-feeling terminal where nothing can go wrong.

~50 minutes Beginner → Confident 8 interactive labs
Start the lesson

You will be able to

  • Explain commits, the staging area and repositories
  • Create a repo, commit, and read its history
  • Work on branches and merge them
  • Push to and pull from GitHub, and fix a rejected push
  • Resolve a merge conflict and open a pull request
  • Keep secrets out of Git with .gitignore

You need: nothing. Helpful: having saved a file on a computer before. Everything happens in simulated terminals, so you can't break anything.

0Chapter 0

Why version control?

Goal: feel the problem Git solves.

You've probably seen folders like essay_final.docx, essay_final2.docx, essay_REALLY_final.docx. That's version control done by hand: slow, messy, and it never tells you what changed between versions.

🎮

Think of it like

Save points in a video game. Whenever things are in a good state, you save. If you mess up later, you reload any earlier save. Git's save points are called commits, and each one records exactly what changed and why.

Lab 0

Snapshots — click one to compare
Pick a snapshot to see what changed since then.
Edit the recipe, then save a snapshot. Repeat a few times.
Try this
  1. Make three snapshots, changing the text between each.
  2. Click an old snapshot and read the comparison: green lines were added since, red lines removed.
  3. Restore an old snapshot. Nothing is lost — your newer snapshots are still there.

That's the heart of Git. Add two more superpowers and you have what every team uses: branches (parallel timelines for trying ideas) and remotes (a shared copy online so people can collaborate). We'll build up to both.

🧭

Git vs GitHub

Git is the program that tracks versions, running on your computer. GitHub is a website that stores Git projects online and adds collaboration tools. Git works fine without GitHub. GitHub is built on Git.

Remember

  • A commit is a named snapshot you can compare with or return to.
  • Git = the tool on your computer; GitHub = the website that hosts Git projects.
1Chapter 1

The three places your work lives

Goal: understand the staging area, the part that confuses every beginner.

A Git project, called a repository (repo), has three areas:

  1. Working folder: the files you see and edit.
  2. Staging area: the changes you've picked for the next snapshot (git add).
  3. Repository: the permanent history of commits (git commit).
📦

Think of it like

Packing a box to post. Your desk is the working folder. The open box is the staging area: you choose which items go in. Sealing and labelling the box is the commit. You can edit three files but put only two in this box, so each commit stays about one thing.

Each commit gets a unique ID (the short code like a1b2c3d) and points to its parent: the commit before it. That chain of parents is your project's history.

      
✍️
Good commit messages
Write what the commit does, in the imperative: "Add contact form", "Fix typo in header". Future-you, reading git log six months from now, will be grateful. "stuff" and "update" help no one.

      
Remember
    
        
  • git init once per project; then the loop is edit → git add → git commit -m.
    • 
        
  • git status tells you where you are; git log tells you where you've been.

3Chapter 3
Branches: parallel timelines

      
Goal: try an idea on a branch and merge it back.

      
A branch is a movable label pointing at a commit. The main line is usually called main. Create a new branch and your commits go there, leaving main untouched. If the idea works, you merge it in. If not, you just abandon the branch.

      
🌿
Think of it like
A parallel universe for your project. You can experiment wildly in one without affecting the other, then bring the good results back.

If main hadn't changed since you branched, Git just slides the main label forward. That's a fast-forward. If both branches got new commits, Git creates a merge commit with two parents, joining the timelines. Try committing on main before merging to see one.

      

        
Check your understanding

  • A branch is a label on a commit; HEAD marks the branch you're on.
    •

4Chapter 4
GitHub: push and pull

      
Goal: sync with GitHub, and fix the most common error beginners hit.

      
So far everything lived on your computer. A remote is a copy of the repository somewhere else, usually GitHub. By convention it's called origin. Two verbs move commits:

      
    
        
  • git push uploads your new commits to the remote.
    • 
        
  • git pull downloads other people's commits and merges them into yours.
    • 
      

      

        
Lab 4
Push, get rejected, pull, push again

        

          

          

            

            

            
Connect this repo to GitHub with git remote add, then push.

          

        

        
Try this
    
          
  1. Add the remote origin.
    2. 
          
  2. Push main to GitHub with git push -u origin main.
    3. 
          
  3. Let a teammate push, then commit your own change and push. Read the rejection.
    4. 
          
  4. Fix it: git pull, then git push again.
    5. 
        

      

      
The rejection isn't an error in your work. It's Git protecting your teammate. The remote has a commit you don't have, and pushing would erase it. git pull brings it in (merging it with yours), and then your push is safe. origin/main in the graph is your computer's memory of where GitHub's main was when you last talked to it.

      
⚠️
Never "force" your way out
You'll find advice online to use git push --force when a push is rejected. On a shared branch that deletes your teammates' commits from GitHub. Pull first. Force-push only to your own branches, and only when you know why.

      
Remember
    
        
  • git push uploads, git pull downloads and merges.
    • 
        
  • "Rejected (fetch first)" means: pull, then push again.
    • 
      

    


    
    

      
5Chapter 5
Merge conflicts, defused

      
Goal: resolve a conflict calmly.

      
Git merges automatically when people changed different lines. If two people changed the same line differently, Git can't know who's right, so it stops and asks you. That's a merge conflict. Git writes both versions into the file between markers:

      
    
        
  • <<<<<<< HEAD: your version starts here
    • 
        
  • =======: divider
    • 
        
  • >>>>>>> origin/main: their version ends here
    •

The workflow is always the same: open the file, choose or combine the versions, delete all three marker lines, then git add and git commit. Code editors like VS Code show "Accept current / incoming / both" buttons, which do exactly what the buttons above do.

      
Remember
    
        
  • A conflict = two edits to the same lines. Git asks a human to decide.
    • 
        
  • Edit the file, remove every marker, then add + commit. Pulling often keeps conflicts small.

6Chapter 6
Forks and pull requests

      
Goal: contribute to a project you don't own.

      
You can't push to someone else's repository; you don't have permission. Instead you fork it (make your own copy on GitHub), make changes on a branch, and open a pull request (PR): a request for the owner to review and merge your branch. Teams use PRs even inside their own repos, because they're where code review happens.

    7Chapter 7
    .gitignore and secrets
    
      
    Goal: never leak a password to GitHub.
    
      
    Some files must never be committed: passwords and API keys (often in a .env file), huge downloaded folders like node_modules/, build output, logs. A file named .gitignore lists patterns Git should pretend don't exist. One pattern per line; * matches anything; a trailing / means a folder.
    
      
    
        
    Lab 7
    Write a .gitignore
    
        
    
          
    
            
    
              
    .gitignore
    
              
    What git add . would commit
    
            
    
          
    
          
    
            
    Will be committed0
    Secrets exposed0
    
            
    
          
    
        
    
        
    Try this
      
          
    1. Ignore the .env file.
      2. 
          
    2. Ignore the whole node_modules/ folder with one line.
      3. 
          
    3. Ignore both log files with a single wildcard line.
      4. 
          
    4. No secrets exposed, and app.js, index.html and README.md still committed.
      5. 
        
    
      
    
      
    🔑
    If a secret reaches GitHub
    Deleting the file in a new commit is not enough: it's still in the history, and bots scan GitHub for keys within minutes. Immediately revoke and replace (rotate) the key with whoever issued it, then clean up. Adding .gitignore first prevents all of this.
    
      
    Remember
      
        
    • Create .gitignore before your first commit.
      • 
        
    • Leaked secret ⇒ rotate it immediately; deleting it isn't enough.
      • 
      
    
    
    

    
    
    
      
    8Chapter 8
    Doing it for real
    
      
    Goal: go from the sandbox to your own computer and GitHub account.
    
      
    1. One-time setup. Create a free account at github.com. Install Git from git-scm.com (on Windows, "Git for Windows"; on a Mac, running git --version offers to install it). Then tell Git who you are. This name and email go into every commit:
    
      
    Terminal · once per computer
    git --version
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main
    
      
    2. Put an existing project on GitHub. On GitHub click + → New repository, give it a name, and leave "Add a README" unticked. Then, inside your project folder:
    
      
    Terminal · inside your project folder
    # create .gitignore first!
git init
git add .
git commit -m "Initial commit"
git remote add origin https://github.com/YOUR-NAME/YOUR-REPO.git
git push -u origin main
    
      
    The first push asks you to sign in. The Git Credential Manager (bundled with Git for Windows) or GitHub's gh auth login handles it through your browser. GitHub no longer accepts your account password on the command line.
    
      
    3. The daily loop. Everything else you do is a variation of:
    
      
    Every day
    git pull                          # start from the latest
git switch -c my-change           # a branch for the task
# …edit files…
git status
git add .
git commit -m "Describe the change"
git push -u origin my-change      # then open a pull request
    
      
    🆘
    Undo cheat codes
    git restore file throws away uncommitted edits to a file. git restore --staged file unstages it. git commit --amend fixes the last commit's message (before pushing). git revert <id> safely undoes a pushed commit by adding a new one.
    
      
    Remember
      
        
    • Setup once: install, git config name/email, sign in on first push.
      • 
        
    • Daily: pull → branch → edit → add → commit → push → PR.
      •
