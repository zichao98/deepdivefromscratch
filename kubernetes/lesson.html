Containers & Kubernetes from zero to hero

"It works on my machine" is the oldest excuse in software. Containers fix it by shipping your app together with everything it needs. Kubernetes then runs hundreds of them across many computers, restarts them when they crash, and updates them without downtime. Learn both in simulated terminals and a live, breakable cluster.

0Chapter 0

Containers vs virtual machines

Goal: understand what a container is, and why everyone uses them.

An app needs more than its code: a language runtime (Node, Python…), libraries at the right versions, config files. Install them slightly differently on two computers and the app breaks on one of them. The fix is to ship the app with its whole environment.

🚢

Think of it like

Shipping containers. Before them, every cargo needed custom handling. After them, cranes, ships and trucks move one standard box without caring what's inside. A software container is a standard box for an app: it runs the same on your laptop, a test server or the cloud.

The older approach, a virtual machine (VM), fakes an entire computer with its own full operating system. Containers instead share the host's operating-system kernel and only package the app and its libraries. That makes them far smaller and quicker to start.

  • Containers are smaller, start in about a second, and run the same everywhere.
1Chapter 1

Images, layers and the build cache

Goal: read a Dockerfile, and order it so builds take seconds instead of minutes.

A container starts from an image: a read-only package of files. You describe how to build one in a Dockerfile (Podman calls it a Containerfile; same format), one instruction per line:

  • FROM node:20-alpine: start from an existing image that already has Node.js.
  • WORKDIR /app: work inside this folder.
  • COPY: copy files from your project into the image.
  • RUN npm install: run a command, here downloading libraries.
  • CMD ["node", "server.js"]: what to run when a container starts.

Each instruction produces a layer. The builder remembers layers, and if an instruction and everything before it are unchanged, it reuses the cached layer instantly. The moment one layer changes, every layer after it must be rebuilt.

Running containers: Docker and Podman

      
Goal: build, run, reach and clean up a container from the terminal.

      
A container is isolated, including its network. The app inside listens on port 3000, but that's the container's port 3000, not your laptop's. To reach it you publish a port: -p 8080:3000 means "laptop port 8080 → container port 3000".

3Chapter 3
Kubernetes: you declare, it maintains

      
Goal: understand desired state, the one idea that explains all of Kubernetes.

      
Running one container is easy. Running 50 across 10 servers, restarting crashed ones, moving them off a dead server: that's the job of an orchestrator, and Kubernetes (K8s) is the standard one. A Kubernetes cluster is a group of machines called nodes. Containers run inside Pods, the smallest unit Kubernetes manages.

      
🌡️
Think of it like
A thermostat. You don't tell it "turn the heater on for 10 minutes". You set 21°, and it keeps measuring and correcting forever. In Kubernetes you declare "3 copies of my app", and a controller keeps comparing reality to that and fixing the difference. This reconciliation loop never stops.

Notice that you never told Kubernetes how to recover, only what you want. That's the difference between declarative ("3 copies") and imperative ("start a container on node 2"). The pieces doing the work live in the control plane: the API server (the front door), etcd (the database of desired state), the scheduler (picks a node for each Pod) and controllers (the reconciliation loops). On every node, the kubelet actually starts the containers.

4Chapter 4
kubectl and YAML

      
Goal: deploy and manage an app the way professionals do.

      
You write desired state in YAML files and send them to the cluster with kubectl, the Kubernetes command-line tool. A Deployment says "keep N Pods running this image". Its labels tag the Pods; its selector says which Pods it owns.

kubectl get lists things, describe explains one in detail (its events are the first place to look when something's wrong), and logs shows a container's output. Statuses you'll meet: Pending (waiting for a node), ContainerCreating, Running, ErrImagePull/ImagePullBackOff (the image name is wrong or not accessible), and CrashLoopBackOff (the app starts and keeps crashing).

      
📁
Why YAML files?
kubectl scale is handy, but the YAML file is the real source of truth. Keep it in Git (see the Git lesson) and your whole deployment is versioned, reviewable and reproducible. Teams take this idea all the way with GitOps.

      
Remember
    
        
  • kubectl apply -f file.yaml declares; get, describe and logs inspect.
    • 
        
  • ImagePullBackOff = bad image name; CrashLoopBackOff = the app keeps crashing.

5Chapter 5
Services: a stable address

      
Goal: understand how traffic finds Pods that keep changing.

      
Pods are temporary: they're replaced all the time, and each new one gets a new IP address. So how does anything connect to them? A Service gives a group of Pods one stable name and address, and spreads requests across whichever Pods currently match its label selector.

Three common Service types decide who can reach it: ClusterIP (default: only inside the cluster, for app-to-app traffic), NodePort (a port on every node's IP), and LoadBalancer (a public address from your cloud provider). 6Chapter 6
Rolling updates and rollbacks

      
Goal: ship a new version without downtime, and undo a bad one.

      
Change the image in a Deployment and Kubernetes performs a rolling update. It starts one new Pod, waits until it's ready, retires one old Pod, and repeats. Users are always served by enough healthy Pods. If the new version is broken, its Pods never become ready, so the rollout stalls with the old version still serving.

For this to work, Kubernetes must know when a Pod is truly ready. You tell it with a readiness probe, for example "GET /health must return 200". Without one, Kubernetes assumes a Pod is ready the moment it starts, and a slow-starting app can receive traffic too early.

      
Remember
    
        
  • Rolling update: add new, wait for ready, remove old, repeat. No downtime.
    • 
        
  • A broken version stalls the rollout; kubectl rollout undo goes back.

7Chapter 7
Doing it for real

      
Goal: run everything above on your own laptop.

      
1. Install tools. Docker Desktop or Podman, plus kubectl and a local-cluster tool: kind (Kubernetes in Docker: fast, great for CI) or minikube (beginner-friendly, lots of add-ons).

      
Build and try the image
docker build -t myapp:1.0 .
docker run -d -p 8080:3000 --name web myapp:1.0
curl localhost:8080
docker rm -f web

      
2. Create a local cluster and load your image into it. Local clusters can't see your laptop's images automatically:

      
kind
kind create cluster --name demo
kind load docker-image myapp:1.0 --name demo
kubectl get nodes

      
or minikube
minikube start
minikube image load myapp:1.0
kubectl get nodes

      
3. Deploy, reach, update. Use the app.yaml from Lab 4 (for a local image, add imagePullPolicy: IfNotPresent under image:):

      
Deploy
kubectl apply -f app.yaml
kubectl get pods -w                       # watch until Running (Ctrl+C to stop)
kubectl port-forward svc/web 8080:80      # then open http://localhost:8080
kubectl set image deployment/web web=myapp:2.0
kubectl rollout status deployment/web
kubectl rollout undo deployment/web       # if something's wrong

      
4. Clean up, in reverse order:

      
Cleanup
kubectl delete -f app.yaml
kind delete cluster --name demo           # or: minikube delete
docker image rm myapp:1.0

      
🔐
Secrets
Never bake passwords into images or plain YAML in Git. Kubernetes has Secret objects, and managed clouds offer secret managers. The same rule as the Git lesson's .gitignore chapter applies.
